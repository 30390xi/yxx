## 客户端加密逻辑

`common/vendor.js:26908-26918` 的 `$eventAnalyse.encrypt(value, key)` 将 `value` 做 `JSON.stringify`，UTF-8 编码后用 CryptoJS AES、ECB 模式、Pkcs7 填充加密，最后直接返回密文字节的小写十六进制字符串。没有在这个函数里附加 IV、盐或 Base64。Java `AES/ECB/PKCS5Padding` 对 AES 块大小产生相同填充，等价实现见 `java8/MiniProgramCrypto.java`。

JDK 8 实现已用测试 JSON `{"event":"browse","n":1}` 与 Node.js AES-128-ECB 独立计算比对，密文均为 `b66c772c74c3cd4922b4f8586baedf2d519948a291f1c66b36de4247b9ea266f`。这验证了该输入的字节级一致性；服务端是否接受实际业务签名仍需真实接口证据。

- 短信验证码相关调用在 `pages/login/login.js:206`、`pages/register/register.js:141`、`subPack/pages/findpassword/findpassword.js:142` 等处使用固定 16 字节密钥 `8nXB5qupfE2mwSeZ`，签名入参包含手机号和毫秒时间戳。具体 JSON 字段以各调用点为准。
- 埋点上报在 `common/vendor.js:26913-26931` 将事件数组用另一固定 16 字节密钥 `xsYc029dbPhO6sI9` 加密，提交 `{data: hex, mode: 1}` 到 `data/app/v1/buriedPoint`。
- 这些是客户端混淆/数据加密行为；是否还有服务端签名校验、其他插件的加密流程，静态包目前未完整证明。
